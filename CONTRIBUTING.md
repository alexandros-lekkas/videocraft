# Contributing to videocraft

videocraft turns a shot script into a cut, measured video filmed inside Minecraft Java 26.3. A Fabric mod plays the
script in a hidden client and captures every frame from the game's own framebuffer; a Python CLI (standard library
only) compiles the script, runs the take, cuts and measures. Thank you for helping.

Read these first; they are short:

- [AGENTS.md](AGENTS.md): the five-minute brief (commands, project map, hard rules, hard-won facts).
- [docs/DESIGN.md](docs/DESIGN.md): the architecture, the run store and the extension point.
- [docs/SCRIPT.md](docs/SCRIPT.md): the script format.

Good first issues are written up in [docs/issues/](docs/issues/) and filed on GitHub with the `good first issue` label.

## Set up in five minutes (macOS with Homebrew)

```sh
brew install openjdk@25 ffmpeg python@3.13     # JDK 25, ffmpeg with libx264, Python 3.11 or newer
git clone https://github.com/alexandros-lekkas/videocraft.git && cd videocraft
bin/videocraft doctor                           # checks the JDK, ffmpeg/ffprobe/libx264, folders, the control port
bin/videocraft run examples/hello.toml          # the first run downloads Minecraft through Loom (a few minutes)
```

That last command ends like this (exit 0 PASS, 1 FAIL, 2 no verdict):

```text
RESULT   PASS 1920x1080 60 fps 180 frames 3.00 s; capture 79.3 fps real time
VIDEO    <repo>/runs/hello/0001/cut/master.mp4
```

Notes:

- Homebrew's `openjdk@25` is keg-only, so Gradle does not find it on its own. `bin/videocraft` finds it itself; for
  raw Gradle, `export JAVA_HOME=/opt/homebrew/opt/openjdk@25/libexec/openjdk.jdk/Contents/Home`. A newer JDK as
  `JAVA_HOME` makes the build fail with "no JDK 25 toolchain".
- You do not need to own or install Minecraft for the build: Loom downloads the game for development into
  `~/.gradle/caches/fabric-loom`. The game runs only in this checkout's `run-game/` folder.
- Verified on macOS (Apple silicon). Linux needs a virtual display and Windows is untested; both are open issues and
  good places to help.

## The commands

```sh
./gradlew build                            # the mod jar (build/libs/videocraft-<v>.jar) + plain-JVM checks
python3 -m unittest discover -s cli/tests  # CLI checks (also refreshes cli/tests/plans/*.plan.json: commit them)
bin/videocraft compile examples/hello.toml # check a script, print the plan; no game
bin/videocraft run examples/hello.toml     # take → cut → measure, as runs/hello/<n>/
bin/videocraft runs hello                  # iterations and verdicts
bin/videocraft cut hello · measure hello   # re-cut / re-measure the latest iteration
bin/videocraft status · stop               # the running client
```

CI runs the build and the CLI checks on every push and pull request. It never launches the game, so the `run` check
is yours to do locally.

## Hard rules

These protect your machine and your game. They are not style preferences, and a pull request that breaks one is not
merged.

1. **Never touch a real Minecraft folder.** Not `~/Library/Application Support/minecraft`, `~/.minecraft`,
   `%APPDATA%\.minecraft`, their `options.txt`, worlds or mods. The game runs only in this checkout's `run-game/`;
   `paths.is_real_minecraft` refuses the others. Do not add an option that points the game elsewhere.
2. **Never commit game assets.** No Mojang textures, sounds, music, fonts or screenshots of them as source art, and
   nothing from `runs/`, `run-game/`, `reference/` or `cache/`. Music and sounds are read from your own local game
   assets at export time. Art in the repo is original and preferably generated by code (see `assets/`).
3. **Hidden, muted, nothing brought to the front.** Takes run hidden (`--show` is for you, by hand), with master
   volume 0, in their own folder, on their own loopback port. No OS input automation and no screen capture: frames
   come from the game's framebuffer.
4. **One client per checkout.** `bin/videocraft stop` when you are done with one you started.
5. **No new Python dependency.** The CLI is standard library only, Python 3.11+.

## Style

- Java 25, tabs, no wildcard imports. Mojang names (26.3 is unobfuscated); check a real class with
  `javap -cp ~/.gradle/caches/fabric-loom/26.3/minecraft-merged.jar <class>` (`-p` for private) before assuming an API.
- Python: 4 spaces, standard library only.
- One idea per commit, with a message that says why. Stage explicit paths (`git add <files>`), not `git add -A`.
- New script keys or actions go in `docs/SCRIPT.md`. A change to the plan shape changes `Plan.java`, `script.py` and
  `docs/SCRIPT.md` together. Run store paths and `frames.csv` columns are only ever added, never renamed.
- A line in `CHANGELOG.md` under *Unreleased*.

## Adding an action or a rig

An **action** is something on a shot's timeline (`{ at = 1.0, do = "<id>", ... }`); a **rig** decides where the camera
is each frame (`camera.rig = "<id>"`). Both are registered by id and created from their parameters, which pass
through the compiler untouched, so a new one needs **no change to `script.py` or `Plan.java`**.

```java
// An action: created when its cue's time comes, then called once per frame until it returns true.
r.action("wait", (p, shot) -> {
	double until = shot.seconds() + p.number("seconds");
	return s -> s.seconds() >= until;
});

// A rig: created when the shot is prepared, asked for a Pose every rendered frame.
r.rig("fixed", Fixed::new);
```

1. **Pick the place.** Built-ins live with their workstream (`director/CoreActions.java`, `camera/Rigs.java`,
   `actor/Actions.java`, `text/TextActions.java`) and register in that class's `register(Registry)`. Another mod
   adds its own through the plugin entrypoint instead (below).
2. **Validate in the factory.** Read parameters with `Params` and throw `IllegalArgumentException` with a message an
   agent can act on ("`radius` must be > 0, got -2"). The take fails naming the script location.
3. **Be a function of the frame clock.** Use `shot.seconds()` / `shot.frame()`, never wall time, and seed any
   randomness from the plan, so the same plan gives the same frames. Keep per-frame work cheap; it runs inside the
   frame budget. Release whatever you added in `Action.stop`.
4. **Threads.** Actions and rigs run on the render thread. World edits and commands belong to the server: post them
   with `shot.command(...)`.
5. **Check the math without a game.** Add cases to a plain-JVM `*Checks` class in `src/smoke/java/` (they run in
   `./gradlew check`); for example `RigChecks` checks angles, easing and the camera operator's spring.
6. **Document it** in `docs/SCRIPT.md` (the action list or the rigs table), and add or extend an example in
   `examples/` that uses it.
7. **Run it and look at it** (next section).

### From another mod (plugins)

```json
"entrypoints": { "videocraft": ["com.example.myshots.MyShots"] }
```

```java
public final class MyShots implements io.github.alexandroslekkas.videocraft.api.VideocraftPlugin {
	@Override public void register(Registry r) {
		r.action("mymod:open_door", (params, shot) -> s -> { /* … */ return true; });
	}
}
```

Plugin ids must carry the plugin's own namespace (`mymod:open_door`); bare ids belong to videocraft, and a duplicate
id is an error. Depend on the videocraft jar as dev-only (`modCompileOnly` + `modLocalRuntime`); players never need
it. The package `…videocraft.api` is the whole contract (see DESIGN.md, "Extension point").

## How visual changes are reviewed

Passing tests says the code runs; it does not say the video looks right. For anything a viewer can see:

1. Run every example your change touches: each must end `RESULT PASS`.
2. Pull frames out of the result into a temporary folder and open them:

   ```sh
   mkdir -p /tmp/vc && ffmpeg -i runs/hello/latest/cut/master.mp4 -vf "select='eq(n\,90)'" -fps_mode passthrough /tmp/vc/f90.png
   ```

   Look at the start, the middle and the end of each shot you changed, and at the frames just after a cut.
   Once `measure` writes it, `measure/contact.png` in the run folder is a contact sheet of the whole cut.
3. In the pull request, say **what you saw** and attach a frame or two. Reviewers re-run the example and look at
   the same frame numbers. "Looks robotic", "the text is too small at phone width" and "the camera bobs" are valid
   review comments; the layout rules (safe area, one message at a time, reading time, capital height) are in
   DESIGN.md section 5 and are measured by `measure`.
4. Determinism matters: two runs of the same plan should give the same frames. If yours do not, say so.

## Reporting bugs and security issues

Use the issue forms: a bug report wants the `RESULT`…`TIME` lines, the log tail and `bin/videocraft doctor`; a shot
that looks wrong wants frames and a look through the run folder. Security issues go privately through GitHub's
advisories; see [SECURITY.md](SECURITY.md).
